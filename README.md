# СППВР — Система поддержки врачебных решений

Локальная (on-premise) клиническая система поддержки принятия решений (CDSS) с ИИ-анализом, работающая **полностью офлайн** — данные пациентов не покидают рабочую станцию (ФЗ-152, HIPAA).

## Возможности

- **ЭМК**: визиты, витальные показатели, препараты, лаборатория, обследования, проблемы, прививки, планы ведения
- **ИИ-анализ кейсов** (llama.cpp `llama-server` / LM Studio): дифференциальный диагноз 3–5 гипотез с аргументами «за/против», план дообследования с приоритетами, терапевтические опции только после подтверждения диагноза, маркеры мониторинга
- **Самопроверка ИИ**: черновик → аудит-проход → финальная версия с отчётом исправлений
- **База знаний**: прямой разбор репозитория клинических рекомендаций Минздрава РФ (cr.minzdrav.gov.ru) + международные источники (PubMed/NLM, ВОЗ, NICE, Cochrane, CDC, ESC, EMA)
- **Проверка лекарственных взаимодействий (DDI)**: потоковый онлайн-поиск в базах РФ (РЛС, Видаль, ГРЛС) + локальная таблица
- **E2EE**: энд-то-энд шифрование карт пациентов (ключ у врача, не на сервере)
- **Аудит**: WORM-журнал действий, экспорт
- **Печать/экспорт**: отчёты PDF, подписи отчётов, экспорт карт
- **Трекер плана дообследования**: статусы (в плане → назначено → выполнено → результат), срок и подготовка, референсы и подсказки по интерпретации, ввод результата со сверкой с нормой; хранится на сервере с аудитом
- **Формальная проверка рекомендаций**: детерминированные правила полноты и согласованности (дифф. ряд, привязка тестов, дозы, источники, аллергии из карты) с баллом и списком замечаний

## Экран результатов анализа

Результат ИИ-разбора открывается как рабочее место врача, а не как сплошной текст:

- **Сводка сверху** — рабочий диагноз и вероятность, объём плана (выполнено/всего), срочные
  исследования, число разблокированных опций терапии, балл формальной проверки.
- **Вкладки**: «Обзор», «Гипотезы», «Обследование», «Терапия», «Контроль», «Источники»,
  «Текст ИИ», «Проверка».
- **Гипотезы** — 3–5 версий с аргументами «за»/«против», красными флагами, МКБ-10 и КР Минздрава.
  Подтверждение диагноза разблокирует терапию и записывается в аудит.
- **Обследование** — трекер: статус, срок, подготовка, норма/пороги, «подтверждает/исключает»,
  руководство по интерпретации и ввод результата с автоматической сверкой с референсом.
  Отметки хранятся на сервере (не в localStorage) и переживают повторный анализ.
- **Терапия** — опции привязаны к гипотезам и заблокированы до подтверждения диагноза.

## Контроль качества рекомендаций

- **Нормализация** (`src/lib/clinical-normalize.ts`) — дубли исследований объединяются, ранги и
  вероятности приводятся к корректному виду, целевой диагноз терапии сопоставляется с гипотезой.
  Все правки перечисляются в разделе «Проверка» — скрытых изменений нет.
- **Формальная проверка** (`src/lib/clinical-audit.ts`) — детерминированные правила: полнота дифф.
  ряда, согласованность вероятностей, наличие аргументов «против», привязка тестов к гипотезам,
  дубли, доза/путь/длительность, источник и уровень доказательности, план контроля, совпадение
  препарата с аллергией из карты пациента. Это проверка формы и полноты, а не замена врачебному суждению.
- **Сохранение решений врача** — подтверждённые диагнозы и отметки трекера переносятся в новую
  версию анализа.
- **Аудит** — изменения статусов, подтверждение диагноза и балл проверки попадают в журнал.

## Быстрый старт

```bash
# 1. Зависимости
bun install

# 2. Конфигурация
cp .env.example .env
# при первом запуске недостающие секреты и настройки допишутся автоматически

# 3. Создать/обновить БД SQLite
bun run db:push

# 4. Запустить
bun run dev          # http://localhost:3000
```

### Первый вход

1. Откройте приложение → тултип статуса в шапке → кнопка **«Инициализировать систему»** (или `POST /api/auth/init`)
2. Система создаст администратора и выдаст **одноразовый пароль** (на экране, не хранится)
3. При первом входе потребуется сменить пароль

> Альтернатива: открытая саморегистрация — `REGISTRATION_OPEN=true` в `.env` (затем верните `false`).

## Подключение ИИ (llama-server)

1. Скачайте модель GGUF (например, Qwen2.5-14B-Instruct-GGUF, Q4_K_M) и запустите сервер:

```bat
.\llama-server.exe -m models\model.q4_k_m.gguf --host 127.0.0.1 --port 8080 -c 16384 -ngl 99
```

2. Проверьте настройки в `.env`:

```ini
AI_PROVIDER=llama-server
LLAMA_SERVER_URL=http://127.0.0.1:8080/v1
LLAMA_SERVER_MODEL=            # пусто = берётся первая модель сервера
```

3. Перезапустите приложение. Статус: дашборд → «Здоровье системы» → «ИИ-сервер».

## Архитектура безопасности

- Всё выполняется локально: БД SQLite, локальное файловое хранилище, локальный LLM. Облачных вызовов с данными пациента нет
- Перед ИИ-анализом выполняется де-идентификация текста (NER)
- E2EE карт пациентов: DEK врача не покидает браузер; сервер хранит только шифротекст
- Секреты сервера (`JWT_SECRET`, `ENCRYPTION_KEY`) генерируются автоматически, ≥ 256 бит
- SSRF-защита: URL ИИ-сервера — только localhost либо явно разрешённые хосты
- Скрипт `ensure-env.ts` восстанавливает отсутствующие настройки подключений при старте, не перезаписывая пользовательские значения

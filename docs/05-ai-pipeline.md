# 05. ИИ-конвейер

## 1. Провайдеры и деградация

| Провайдер | `AI_PROVIDER` | Порт по умолчанию | Примечание |
|---|---|---|---|
| llama.cpp `llama-server` | `llama-server` | 8080 | `-ngl 99`, `--mmproj` для vision |
| LM Studio | `lm-studio` | 1234 | Developer → Start Server |
| Ручной режим | — | — | LLM недоступен → анализ без ИИ |

- Оба провайдера — **OpenAI-compatible** `/v1/chat/completions` (`src/lib/lm-studio.ts`).
- `getActiveProvider()` кэширует health на 15 с; при недоступности возвращает `none`,
  и конвейер работает в **ручном режиме** (документы, NER-метаданные, детерминированные
  справочники — без генерации заключения).
- Повторы: `LM_STUDIO_MAX_RETRIES`, экспоненциальная задержка `base × 3^(n-1)`.
  Пустой/короткий ответ (< 20 символов для JSON, < 50 для текста) считается обрывом.
- **SSRF-защита**: разрешены только `localhost`, `127.0.0.1`, `::1` и хосты из
  `LM_STUDIO_EXTRA_ALLOWED_HOSTS` (алиас `AI_EXTRA_ALLOWED_HOSTS`). Иной хост → откат
  на дефолтный URL и запись в лог.

> Параметры `AI_*` имеют приоритет над `LM_STUDIO_*`: `AI_ENABLED`, `AI_URL`, `AI_MODEL`,
> `AI_API_KEY`, `AI_EXTRA_ALLOWED_HOSTS` — общие алиасы, провайдероспецифичные переменные
> (`LLAMA_SERVER_*`, `LM_STUDIO_*`) переопределяют их.

## 2. Де-идентификация (до модели)

```
rawContent ──► deidentify.ts (regex: ФИО, СНИЛС, полис, телефон, e-mail, адрес, даты)
           ──► ner-deidentify.ts (локальный NER-словарь)
           ──► deidContent  ──► промпт LLM
```

- В модель уходит только `deidContent`; исходный текст остаётся на сервере.
- Для внешних поисковых запросов дополнительно работает `query-sanitizer.ts`:
  из запроса удаляются ФИО, точные даты, адреса, номера документов, названия учреждений.
- Проверка «есть ли PHI» — `containsPHI` / `textContainsPHI` (используется в тестах и
  в аудите загрузки).

## 3. Конвейер `POST /api/cases/{id}/analyze`

```
0. Auth + consent gate (ai_analysis)           ── 403 CONSENT_MISSING / CONSENT_EXPIRED
1. NER по выпискам                             ── сущности + цитаты + мутации
2. Интерпретация генетических вариантов        ── VCF/CSV/LLM
3. Анализ изображений (VLM)                    ── findings + suspicion
4. RAG: локальная БД КР                        ── рекомендации, доказательность
4.5 Web RAG: cr.minzdrav.gov.ru + междунар.    ── фрагменты КР, PubMed/WHO/NICE/…
5. Фармакогеномный кросс-чек                  ── предупреждения по мутациям
6. DDI                                          ── локальная таблица + онлайн
7. МКБ-10                                       ── коды-кандидаты
8. Клинические пути                             ── соответствие протоколам
9. Заключение ИИ                                ── диф. диагноз → обследование → терапия
   ├─ 9.1 самопроверка (AI_DEEP_ANALYSIS)
   ├─ 9.2 JSON-структуризация (zod)
   ├─ 9.3 sanitizeClinicalStructure
   └─ 9.4 auditAnalysis (26 правил)
10. Сохранение: AnalysisVersion (снапшот) → AnalysisResult (vN+1) → AuditLog
```

Каждый шаг обёрнут в `try/catch`: сбой одного источника (например, недоступен PubMed) не
валит анализ. Внешний `catch` возвращает кейс в `uploaded` и отдаёт `500` с текстом ошибки.

### 3.1 Контекст, который видит модель

- Текст выписки (де-идентифицированный, до 4000 символов).
- Мутации, рекомендации RAG, DDI-алерты, коды МКБ-10, клинические пути, findings изображений.
- Сущности из выписки (диагнозы, препараты).
- EMR-блок: пол, возраст, группа крови, аллергии, активная терапия, проблемы, витальные,
  отклонённые лабораторные значения.
- Фрагменты КР Минздрава и международных источников (явно отделены маркерами).

### 3.2 Промпт-контракт заключения

Роль: «виртуальный врачебный консилиум» (терапевт, кардиолог, пульмонолог, онколог,
фармаколог, эндокринолог, невролог, инфекционист, генетик, лабораторный диагност,
рентгенолог, специалист клинических путей). Адресат — лечащий врач.

Разделы ответа (строго `### НАЗВАНИЕ`):

1. `КЛИНИЧЕСКАЯ КАРТИНА` — только факты из документов + «Данных не хватает: …».
2. `ДИФФЕРЕНЦИАЛЬНЫЙ ДИАГНОЗ` — 3–5 гипотез по убыванию вероятности, каждая:
   `Аргументы за`, `Аргументы против`, `Для подтверждения`, `Красные флаги`, `Чем различить`.
3. `НЕОБХОДИМОЕ ДОПОЛНИТЕЛЬНОЕ ОБСЛЕДОВАНИЕ` — один тест = один буллит:
   приоритет · зачем · срок · подготовка · подтверждает/исключает гипотезу · ожидаемый
   результат · норма · критерии «подтверждает, если» / «исключает, если» + строка
   `Интерпретация: …`.
4. `ТЕРАПЕВТИЧЕСКИЕ ОПЦИИ ПОСЛЕ ПОДТВЕРЖДЕНИЯ ДИАГНОЗА` — «Если подтверждён [диагноз]:»,
   МНН, доза с единицами, путь, кратность, длительность, обоснование, уровень
   доказательности, источник, предупреждения.
5. `МАРКЕРЫ И МОНИТОРИНГ` — маркер · цель · частота.
6. `ЛЕКАРСТВЕННЫЕ ВЗАИМОДЕЙСТВИЯ (DDI) И ПРЕДУПРЕЖДЕНИЯ`.
7. `КЛИНИЧЕСКИЕ ПУТИ`.
8. `РЕЗЮМЕ`.
9. `УВЕРЕННОСТЬ` — `diagnosis/therapy/prognosis/overall` в 0..1.

Жёсткие правила фактов:

- Нельзя домысливать анамнез (курение, алкоголь, аллергии, профессия, наследственность).
- Нельзя приписывать симптомы/значения, которых нет в данных.
- Все цифры — только из данных; собственные оценки помечать «ориентировочно».
- Нельзя выдумывать коды КР и МКБ-10.

Требования к качеству (проверяются автоматически):

1. 3–5 гипотез; вероятности строго убывают, сумма ≤ 100%.
2. ≥ 2 аргумента «за» (с привязкой к факту) и ≥ 1 «против» у каждой гипотезы.
3. Каждая гипотеза проверяема: тест, который подтвердит, и тест, который исключит.
4. Один тест — один пункт; «СРБ» и «СРБ, количественно» — дубль.
5. Запрещены исследования, не меняющие тактику («на всякий случай», повтор без срока).
6. Доза обязательна с числом и единицами; при зависимости от веса/почек — формула и порог.
7. Сверка с аллергиями и постоянной терапией из EMR; при совпадении — альтернатива.
8. Для каждого красного флага — немедленное действие.
9. Код МКБ-10 — только корректный для гипотезы.

### 3.3 Самопроверка (verification pass)

При `AI_DEEP_ANALYSIS=true` и `AI_SELF_VERIFY_PASSES=N`:

1. Черновик заключения отправляется модели с задачей аудита: факты против исходных данных,
   полнота диф. ряда, преждевременная терапия, дозы, источники, «вода».
2. Модель возвращает исправленную версию + список исправлений.
3. `extractVerificationReport` отделяет блок исправлений; очищенный текст идёт дальше.
4. Результат — `structured.verification`:
   `{ performed, passes, corrections[], factsGrounded, verifiedAt }`.

`factsGrounded` — консервативная эвристика: `true`, если в отчёте нет слова «выявлено» и
исправлений нет. Это **не** гарантия истинности, а индикатор.

### 3.4 Структуризация

Основной путь (`src/lib/structured-extraction.ts`):

```
финальный текст ──► LLM «структуризатор» (json: true, temperature 0.1, 5120 токенов)
               ──► parseJSON (снимает ```json и находит первый объект)
               ──► aiStructuredSchema (zod)
               ──► normalizeStructured (ранги, вероятности, обрезка)
               ──► Partial<AnalysisStructured>
```

Если структуризатор вернул невалидный JSON — откат на эвристический разбор текста
(`parseStructuredFromText`: regex по «Гипотеза N:», полям «Аргументы за:», «Норма:» и т.п.).
Эвристика хрупкая, поэтому основной путь — JSON.

### 3.5 Детерминированная нормализация

`sanitizeClinicalStructure(structured)` (`src/lib/clinical-normalize.ts`) до сохранения:

| Исправление | Пример |
|---|---|
| Удаление пустых названий | гипотеза/тест/препарат без названия |
| Дедупликация гипотез | одинаковые названия → одна |
| Вероятность → доля | `65` → `0.65`, clamp 0..1 |
| Перенумерация рангов | 1, 1, 3 → 1, 2, 3 |
| Объединение дублей исследований | «СРБ» + «СРБ, количественно» → один пункт, приоритет — максимальный, поля сливаются |
| Сопоставление `targetDx` | «пневмония» → «Внебольничная пневмония, средней тяжести» |
| Дедупликация терапии | одинаковый препарат + целевой диагноз |
| Пометка отсутствующей дозы | фиксируется в `normalizationFixes`, доза **не выдумывается** |

Все исправления попадают в `structured.normalizationFixes` и видны врачу во вкладке
«Проверка». Клинический смысл не переписывается.

### 3.6 Перенос решений врача

`carryOverDoctorState(previous, next)` при повторном анализе:

- `confirmedDx` — только диагнозы, оставшиеся в новом диф. ряду;
- `workupTracker` — только исследования, оставшиеся в новом плане (ключ — нормализованное
  название);
- перенесённые значения пишутся в `AuditLog` (`carriedConfirmedDx`, `carriedWorkupNotes`).

## 4. Формальная проверка рекомендаций

`auditAnalysis({ structured, citationsCount })` — 26 правил, веса: critical 18, warning 7,
info 2; `score = max(0, 100 − Σвесов)`; `readiness`: ≥85 high, ≥65 medium, иначе low
(пустой диф. ряд — всегда low).

| id | Уровень | Условие |
|---|---|---|
| `dx-empty` | critical | Нет ни одной гипотезы |
| `dx-few` | critical | Гипотез < 3 |
| `dx-probability-order` | warning | Вероятности не убывают по рангу |
| `dx-probability-sum` | warning | Сумма вероятностей > 105% |
| `dx-probability-missing` | warning | Все вероятности 0/пусты |
| `dx-weak-support` | warning | У гипотезы < 2 аргументов «за» |
| `dx-no-counter` | warning | Нет аргументов «против» |
| `dx-no-workup` | warning | Нет обследования для гипотезы и нет привязки в плане |
| `dx-no-redflags` | info | У ведущей гипотезы нет красных флагов |
| `dx-no-sources` | info | Нет источников ни у гипотез, ни в цитатах |
| `workup-empty` | critical | Диф. ряд есть, план пуст |
| `workup-no-link` | warning | Нет ни цели, ни привязки к гипотезе |
| `workup-no-purpose` | info | Привязка есть, «зачем» не описано |
| `workup-duplicates` | warning | Дубли (с учётом уточняющих слов) |
| `workup-no-reference` | info | Лабораторный тест без нормы/критерия |
| `workup-no-urgent` | info | Нет срочных при вероятной ведущей гипотезе (≥ 60%) |
| `therapy-orphan` | critical | `targetDx` не совпадает ни с одной гипотезой |
| `therapy-no-target` | critical | Терапия без целевого диагноза |
| `therapy-no-dose` | warning | В режиме нет ни одной цифры |
| `therapy-no-caution` | warning | Нет предупреждений/противопоказаний |
| `therapy-no-source` | warning | Нет источника |
| `therapy-no-evidence` | info | Нет уровня доказательности |
| `monitoring-empty` | warning | Терапия есть, мониторинга нет |
| `monitoring-incomplete` | info | Нет частоты или цели контроля |
| `safety-allergy` | critical | Препарат совпадает с аллергией из `patientSafety` |
| `verification-not-run` | info | Самопроверка не выполнялась |

Правила **не оценивают медицинскую истинность** — только полноту и внутреннюю согласованность.
Это прямо оговорено в интерфейсе.

## 5. RAG и внешние источники

| Слой | Модуль | Что делает |
|---|---|---|
| Локальная база | `rag.ts` + `seed/clinical-recommendations.ts` | Поиск КР по ключевым словам/гену/категории, кросс-чек терапии |
| КР Минздрава РФ | `minzdrav-cr.ts`, `minzdrav-rag.ts` | Поиск по `apicr.minzdrav.gov.ru`, разбор секций, кэш в `MinzdravCache` |
| Web RAG | `web-rag.ts` | Комбинирует КР Минздрава и международные источники, строит контекст |
| Международный | `international-rag.ts` | PubMed/NLM, ВОЗ, NICE, Cochrane, CDC, ESC, EMA |
| Сеть | `network-health.ts` | Probe, circuit breaker, `safeFetch`, кэш статуса |

- Внешние результаты **не являются** частью заключения: они подмешиваются как контекст
  с указанием источника.
- При отсутствии интернета конвейер продолжается на локальной базе; статус отображается
  в UI («Нет интернета»).
- Кэш Минздрава: `MinzdravCache(cacheKey unique, kind, payload, fetchedAt, expiresAt)`.

## 6. DDI (лекарственные взаимодействия)

`src/lib/ddi-online.ts`:

1. Нормализация брендов РФ → МНН (словарь).
2. Локальная таблица `DrugInteraction` (`drug1+drug2` unique).
3. Онлайн-поиск по источникам РФ (РЛС, Видаль, ГРЛС), кэш `DdiOnlineCache` (sha1 пары).
4. Извлечение взаимодействия моделью из найденных фрагментов.
5. Потоковая выдача событий (`POST /api/ddi/stream`, см. 04-api.md §6).
6. Решение врача по алерту фиксируется `POST /api/cases/{id}/ddi-override` с аудитом.

## 7. Что ломается и как это видно

| Симптом | Вероятная причина | Что смотреть |
|---|---|---|
| `structured` пустой, текст есть | структуризатор не вернул JSON | лог `structured-extraction`, длина ответа, `AI_MAX_TOKENS_ANALYSIS` |
| Гипотез 1–2 | модель «уверена», промпт не удержал | `dx-few` в проверке; повторить анализ |
| Терапия заблокирована у всех | `targetDx` не совпал | `normalizationFixes`, `therapy-no-target` |
| `therapy-no-dose` | модель не указала режим | карточка терапии, повторить с более крупной моделью |
| `safety-allergy` | аллергия из карты | карта пациента, `patientSafety` |
| Анализ падает 500 | ошибка шага/БД | `AuditLog`, `SystemLog`, `logger.error("analysis")` |
| Долго (> 10 мин) | CPU-модель, большой контекст | уменьшить `INTL_RAG_MAX_RESULTS`, `AI_SELF_VERIFY_PASSES=0` |

## 9. Ограничения подхода

- LLM не является медицинским изделием; вывод — **рекомендация**, не диагноз.
- Вероятности гипотез субъективны и не калиброваны; аудит проверяет только их
  согласованность (порядок, сумма).
- Детерминированные правила ловят форму, а не факт: препарат с правильной дозой может быть
  клинически неверным. Поэтому терапия заблокирована до подтверждения диагноза врачом.
- Де-идентификация снижает, но не исключает риск ре-идентификации по редким признакам.
- Модель может «галлюцинировать» источник; UI маркирует источники и требует проверки.
